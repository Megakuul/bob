## DECISIONS
- A390 (F2) GetCheckoutCredential (Checkouts.held, used by Lease and Get) accepts a job only when
  (1) job/<id> names the caller as owner at that epoch, claimed or running (as before), (2) its
  spec decodes, is signed by an orchestrator key (the queue's key or fleet/cfg.k) and names this
  job id, and (3) the lease binding in the control bucket (ftok/<sh2(job)>.l[job] = {wid, epoch,
  at}; workers cannot write the control bucket) is this worker at this epoch, or is created now.
  A binding moves to another worker, or to a later epoch, only when the bound worker's lease is
  over by the reconciler's own rule, judged from state only that worker can write: its worker
  record is revoked/gone/absent, or its heartbeat is absent, not signed by its key, older than
  lease_ttl + skew, or (newer than the binding) no longer lists the job. Older epochs never come
  back. The sweeper drops a binding only when job/<id> is gone (finalised by an orchestrator); a
  terminal state is no reason (workers can write it). All refusals keep the single R-FLEET-006
  text `permission_denied: worker holds no lease on job <id>`. Residual, documented in the
  runbook: any worker may claim any queued job of a class it serves (shared fleet by design), so
  a compromised worker still gets the credentials of jobs it claims. Cost: +1 GET fleet/cfg and
  +1 GET (+1 PUT on the first call) of the ftok shard per GetCheckoutCredential, outside the
  enqueue/claim/start/result/finalise path that R-FLEET-009 counts.
- A391 (F1, job binding) Promotion requires the job's evaluation report (<staging>eval.json,
  SHA-256 = the owner-signed JobResult.EvalSHA). Every staged path must be a report package
  output or reachable from one through the claimed references of staged paths; otherwise
  `failed: artifact verification`. The promotion also requires spec.JobID == record id (a signed
  spec copied into another record). This is the smallest rule from what the orchestrator holds:
  the drv-to-output mapping is not available to it (it would have to evaluate), and the report
  is written by the same worker (evalbuild self-attestation), so the binding narrows staging to
  the worker's own claim about the job; it is not a proof. Limits inherited from the report
  (10,000 packages, 256 outputs per package): a larger honest job would fail; accepted.
- A392 (F1, cross-project conflict) A staged path that is already published with other bytes:
  if the job's project is in the visibility document it is the project's own non-reproducible
  path (R-REG-152 (3), unchanged); if not, the path belongs to other projects: the job gets no
  visibility, does not record the path in its non_reproducible (so one project's worker never
  marks another project's path), the orchestrator logs `security: path conflict` (path, project,
  publishing projects, worker), and the job's other paths are promoted (no build failure for an
  honest project that shares a non-deterministic derivation). Published bytes are never
  replaced and never shown to a project that did not stage them identically. Not achieved: when
  a compromised worker publishes a not-yet-served path first, the victim project gets 404 for
  that path (it builds it locally; its releases containing it fail) until the operator removes
  the squatted entries. Serving the victim its own bytes would need per-project narinfos for one
  store path (a change of the D58 visibility model), and any rule that lets the second publisher
  displace the first lets an attacker displace honest publications. See NEEDS.
- A393 (F3) Workers GET (not HEAD) the upstream narinfo of every closure path and stage the
  answer for skipped paths at <staging>upstream/<hash>.narinfo. The orchestrator counts a
  skipped path as upstream only when that narinfo names the path and carries a signature by one
  of promote.Config.UpstreamKeys (default cache.nixos.org-1, the key of SPEC §6.6.5); it never
  contacts cache.nixos.org itself (R-REG-005 and TestRREG005CacheHasNoOutboundHTTPClient hold).
  An unverified skipped path neither excuses a claimed reference (it must then be in the job or
  served, else unknown-reference wait/fail as before) nor a store hash inside a kinds output.
  This corrects A149's rationale ("a worker cannot smuggle foreign paths"): it held only for
  verified skipped paths; please amend A149 in plan/decisions.md accordingly.
- A394 (F5/F1 release) Release creation (step 1, before anything is public) walks the closure
  and fails when a bob-served closure path's visibility document does not list the release's
  project, when a closure path is in the build's non_reproducible (BuildRecord.nr), or when an
  image object's OCI visibility document does not list the project.
- A395 (F6) docs/operations/worker-compromise.md and R-SEC-101 restate the guarantees: claimable
  queued jobs of any project, readable artifacts bucket, poisoning limited to jobs held,
  squatting of unpublished paths (DoS, no byte crossing), audit from orchestrator-written state
  (build records' job rows, promotion log promo/, orchestrator logs), never from bob-analytics.
- A396 (F8) internal/netguard: outgoing forge API calls and notification deliveries refuse, at
  connect time after DNS resolution (only vetted addresses are dialed), loopback, RFC 1918/ULA,
  link-local (IMDS), CGNAT, unspecified, multicast, reserved/documentation ranges, and
  IPv4-mapped/NAT64 forms of them, unless server.outbound_allow (BOB_SERVER_OUTBOUND_ALLOW,
  host names, IPs, CIDRs; invalid entries refuse the start) allows them. Proxies from the
  environment stay usable; the proxy's address is checked like any other. -tags bobtest builds
  allow loopback (only) without configuration: the harness stacks run forges and receivers on
  loopback and do not set BOB_TEST_HTTP_LOOPBACK, and those protected tests cannot change. The
  forge adapters keep an unguarded default client (tests/forge drives adapters directly on
  loopback); the server reaches adapters only through integration.Registry, which always applies
  its Outbound policy (nil = public addresses only). Notifier.New starts guarded.
- A397 (F7) The checkout credential reaches git via GIT_CONFIG_COUNT/KEY_0/VALUE_0 in the fetch's
  environment (git >= 2.31; readable only by the worker's uid), never on a command line.
- A398 (F4) More than 256 distinct unknown /nix/store/<hash> strings in a NAR fail verification
  for every path (strict or kinds): the scan no longer drops the rest silently.

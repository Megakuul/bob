## Analysis of the PIPE005 (3) counts (I-B26 STILL RED 2)
Pipeline ci of acme is `Tests: //...`: the evalbuild job runs `bob test` over two test units, so
a build has 4 report nodes (2 test-unit packages + 2 test results). The I-B26 numbers decode as:
- original {Cached 1, Failed 2, Skipped 1}: unit A (cmd/api, broken test) package failed + test
  fail; unit B (unchanged since the first main build) test `cached` (its result was valid in
  that worker's store) and its package `skipped` (pkg/engine/build/pipeline.go collect: a
  requested label Nix had nothing to do for becomes `cached`, but `skipped` when the run exited
  non-zero, although its outputs are valid);
- retry {Built 2, Failed 2}: A failed again (right), B built and passed again: the retry ran on
  the devstack's other worker (devstack -workers 2), whose store did not have B.
Unit B's outputs were already promoted by the first (succeeded) main build, so staging a failed
job's outputs (task 1, A200) is necessary in general but did not cause this run's rebuild.
The rebuild comes from two gaps outside this unit's packages:
1. Workers never substitute from bob's cache: SPEC §05.8 says the job container's nix.conf has
   `substituters = <bob cache> https://cache.nixos.org`, and §6.9.6 /
   GetCheckoutCredentialResponse.download_token ("bob_dt_, download scope, the job's project
   only, deleted at job end") gives the job a credential for it. cmd/bob-server/parts_fleet.go
   sets no worker.ProcessConfig.Substituters/TrustedKeys and internal/fleetsrv checkout() fills
   no download_token, so the container's nix.conf lists only cache.nixos.org (NEEDS 1).
2. The engine's `skipped` for a valid, untouched requested package in a failed run (NEEDS 2):
   with gap 1 closed, a retry on the other worker substitutes B (`cached` package + `cached`
   result = Cached 2, Skipped 0) while the original on the warm worker reported Cached 1,
   Skipped 1, so `rb.Counts.Skipped != failedBuild.Counts.Skipped` would still fail.
Within this unit, A202 (retry/re-run jobs prefer the worker that ran the repeated build) makes
the warm worker the first one woken for the retry, where the counts are reproduced exactly.

## DECISIONS
- A200 Outputs of packages that built inside a failed evalbuild job are staged and promoted
  (SPEC §6.9.5 "RetryBuild … succeeded packages are cache hits", R-PIPE-005 (3) "others
  CACHED/SUCCEEDED unchanged"). The runner computes the closure of the built/cached outputs also
  when the job failed (a closure error then only drops the staging, the job stays failed); the
  worker stages NARs + claims + COMPLETE.json for it (no images, no release assets; a staging
  error leaves the job failed without COMPLETE.json, never infra); JobResult keeps status
  `failed` and names the COMPLETE.json. promote.Awaits(job) = succeeded, or failed with a
  COMPLETE.json, and no verdict yet; the promoter verifies such a job exactly like a succeeded
  one (§6.6.4 steps 1-3, 6) and refuses a failed job's COMPLETE.json that lists images or assets
  (`failed: artifact verification`). The build controller finalises such a job only after its
  verdict (as for succeeded jobs, also in settle); a `blocked` verdict of a failed job does not
  run it again (nothing to recover); a `failed` verdict adds `promotion: …` to the build
  errors as before. Verdict and job state stay separate fields (pm vs st), as the SPEC has them.
  Rejected alternatives: per-node COMPLETE files (same verification, more objects); promoting
  only on retry (the retry may run anywhere, later, after staging expired).
- A201 The evaluator trusts `.bob/eval` only when bob's ownership stamp matches: the file
  `.bob/eval/owner` holds device, inode and change time (ns) of the lock file bob created there.
  ctime is set by the kernel and cannot be chosen by a user, so a committed / copied / extracted
  `.bob/` never matches; it is emptied (except the lock bob holds) and the evaluation starts
  cold. The lock is now taken before anything below .bob/eval is read (index.json fed the
  hashes) and opened O_NOFOLLOW (a committed `lock` symlink was followed with O_CREATE as root
  on workers); a non-regular lock is removed and recreated. Developer checkouts lose their warm
  evaluator state once after the upgrade (one cold compile). Rejected: deleting `.bob` in the
  worker checkout only (the evaluator would still trust copied state elsewhere); moving the
  state out of the repository (paths inside the sandbox are /src-relative, large change).
- A202 Jobs of a retry or re-run build carry Prefer = the worker that ran the last job of the
  same kind and class in the build they repeat (RetryOf/RerunOf → ByNumber → its job rows).
  Prefer is the SPEC's affinity hint (R-FLEET-012 wake order only), so placement stays
  best-effort; it makes local cache hits the common case while workers cannot substitute from
  bob's cache (NEEDS 1) and keeps them cheap after that.

## NEEDS
1. cmd/bob-server + internal/fleetsrv + internal/auth/cache owners (SPEC §05.8, §6.9.6): job
   containers must substitute from bob's cache: (a) worker.ProcessConfig.Substituters/
   TrustedKeys from the orchestrator's /nix URL and nix.public_keys (cmd/bob-server
   parts_fleet.go; the nix.conf is written once per worker process, so the credential must
   come per job, e.g. a netrc in the job's home); (b) GetCheckoutCredential fills
   download_token (bob_dt_, scope download, the job's project only, revoked at job end) and the
   worker hands it to the job's Nix (netrc). Without it a retry on another worker rebuilds every
   package the original build had built (PIPE005 (3) on a 2-worker devstack).
2. pkg/engine/build owner (pipeline.go collect): a requested label without Nix activity is
   reported `skipped` when the run exited non-zero, also when its outputs are valid. It should
   be `cached` when its outputs are valid in the store (and `skipped` only when they are not);
   otherwise the counts of a failed build depend on which worker's store was warm.
3. internal/orchestrator owner (reconcile.go ~380): the reconciler finalises terminal jobs after
   FinaliseAfter (10 min) unless `succeeded && pm == ""`. Use `promote.Awaits(rec)` instead so a
   failed job with staged outputs (A200) also keeps its record until its verdict (today a
   promotion slower than 10 min would lose those outputs; correctness is unaffected: the job
   stays failed, staging expires).

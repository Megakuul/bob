# I-B44 — build inputs read-only (R-FLEET-008 / R-SEC-000 hostile build)

Status: done (see "Tests"). Follows I-B42 NEEDS 1 ("Still failing": TestRFLEET008BuildsAreIsolated,
TestInputStorePathsAreReadOnly reporting chmod/write on every input).

## Root cause (measured)
1. **Rootless store (dev profile, R-NIX-021/024).** bob's namespace maps `0 → <user>` only and
   nix.conf has `build-users-group =` (pkg/engine/store/layout.go:113). Nix 2.34.9 then builds
   with no build user: its sandbox userns maps the sandbox uid 1000 to `getuid()` of the Nix
   process (= 0 in bob's ns = the user), see nix-2.34.9
   `src/libstore/unix/build/linux-derivation-builder.cc` (`uid_map` "sandboxUid hostUid 1").
   Inputs are bound into the chroot with `mount(src, dst, "", MS_BIND|MS_REC)` (`doBind`), i.e.
   writable, and Nix relies on ownership alone. Every store file belongs to the user, so the
   build (same kuid) is the owner: `chmod 0777` succeeds, then a write into the 0555 directory.
   Local repro as `bobtest` (go fixture + the test's hostile_test.go, `bob test
   //lib/hostile:go_test`): 13 paths reported (glibc, go-1.26.8, bob-builder-16, bash, ...), and
   the persistent private store was really modified (deleted afterwards).
2. **$out in the listing.** test-run created `$out` (owned by the build uid, necessarily
   writable) before starting the test, so `TestInputStorePathsAreReadOnly`, which walks all of
   `/nix/store`, also found `…-go-test-example.com-lib-hostile-run` (the test's own output). This
   hits the root worker too: there Nix runs as real root with `auto-allocate-uids` (the store is
   root-owned, inputs were already safe), but the allocated build uid owns `$out`. Most likely the
   only reason the remote run of TestRFLEET008 failed (not measured with the old builder; the
   per-test output was not retrievable in I-B42).

## Fix
- **bob-builder locks its inputs before any job code runs** (pkg/builder/inputs.go,
  `builder.LockInputs`, called first in cmd/bob-builder/main.go):
  1. outer (pid 1 of Nix's sandbox) lists the mounts strictly below `$NIX_STORE` from
     /proc/self/mountinfo; if any is writable it starts itself as `bob-builder(locking-inputs)`
     with `CLONE_NEWUSER|CLONE_NEWNS`, uid/gid mapped to themselves (build keeps uid 1000/gid 100,
     outputs owned exactly as before), `setgroups deny`, ambient `CAP_SYS_ADMIN`; after the start
     it makes itself non-dumpable and releases the child through a pipe (fd 3);
  2. locking: remounts every store mount `MS_REMOUNT|MS_BIND|MS_RDONLY` plus the flags it already
     has (statfs; locked flags must be kept), re-checks mountinfo, clears the ambient set on its
     thread and execs itself as `bob-builder(inputs-read-only)` → non-root uid, no capabilities;
  3. locked: re-checks "no writable store mount" and `CapEff == 0`, then runs Main.
  The chroot's store directory itself stays writable (outputs are created there). Without any
  mount below the store (builder run outside a sandbox) nothing changes. If locking is impossible
  the build fails closed with `bob-builder: cannot make the build inputs read-only: <reason>`.
- **test-run creates `$out` only after the test** (pkg/builder/testrun.go): the log is written
  to an unlinked temp file in the build dir and copied to `$out/test.log` afterwards (O_EXCL,
  O_NOFOLLOW as before); test-result.json unchanged.
- BuilderVersion 16 → 17 (pkg/builder/bspec/bspec.go), `go generate ./pkg/engine/store`
  (builders.go: aarch64 `…hs90yr9c8s1zm190cxnxpw29885d4hsg-bob-builder-17`, x86_64
  `…3pcfi7sfqz8kcr39szr3rzzbhpfw1sw2-bob-builder-17`; builderbin/*/bob-builder.gz). All bob
  derivation hashes change with the builder path (expected for a version bump); no golden holds
  the builder path (grep).
- Worker container (internal/isolation): no change needed. Its `/nix` must stay writable for Nix
  (root inside the container); inputs are root-owned and builds run as auto-allocated uids, and
  the same bob-builder lock now adds read-only mounts on top (defence in depth).

## Threat analysis
Attacker: code that runs inside a build (user test code, build scripts, compilers fed hostile
input) — on a developer machine (rootless) or on a shared root worker (other projects' builds).
| Vector | Before | After |
|---|---|---|
| chmod/write/unlink inside an input path (`/nix/store/<in>`) | rootless: succeeds (build uid owns the store); worker: EPERM (root-owned) | EROFS everywhere (read-only bind in the build's mount ns) |
| Remount the input rw (`mount -o remount,rw`) | n/a | needs CAP_SYS_ADMIN in the nested ns: the job has none (CapEff checked = 0, non-root uid, NO_NEW_PRIVS from Nix, no setuid files in the store) |
| New userns inside the build, then remount rw | n/a | mounts copied into a less privileged ns are locked (MNT_LOCK_READONLY): EPERM |
| Reach the writable view through pid 1 (outer bob-builder, still in Nix's mount ns): `/proc/1/root/nix/store/<in>`, `/proc/1/fd`, ptrace | — | outer is non-dumpable (PR_SET_DUMPABLE 0) before any job code; measured: EACCES (even without it on this host: EACCES — kept as defence in depth, not relied on alone) |
| Rename/rmdir an input mount point in the chroot store dir | — | EBUSY (mount point); the chroot dir is discarded after the build anyway |
| Tamper with the test's own log/result while it runs | `$out/test.log` writable by the test | `$out` absent during the test; log is an unlinked fd of the builder |
| Spoof the stage markers (argv0) | — | argv0 comes from the derivation bob generates; the locked stage re-verifies mounts and caps itself, so a wrong argv0 cannot skip the lock |
| Fake "already read-only" | — | decided from /proc/self/mountinfo of the process, not from env/args |
| Lock impossible (nested userns refused, e.g. max_user_namespaces=0 inside) | — | build fails closed with a named reason (no silent fallback) |
Residual (not in this unit's scope, NEEDS 1): processes bob starts in its namespace outside Nix
builds (`bob exec`, `bob dev`, shims, IDE tools) run as the store owner (uid 0 in bob's ns =
the user) and can still modify the store; they run the user's own commands, not hostile builds.

## DECISIONS
- A370: input store paths are made read-only by bob-builder itself in a nested user + mount
  namespace (ro bind remount of every mount below the store), not by changing how Nix runs: Nix
  2.34.9 binds inputs writable and only build users (impossible rootless with a single uid
  mapping, R-NIX-021) or a root-owned store protect them; patching Nix is out (embedded nixStatic
  pin, R-NIX-020). Applies to rootless and worker alike; the build keeps uid 1000 and output
  ownership, so outputs are byte-identical apart from the builder path change.
- A371: test-run creates `$out` after the test has ended (log buffered in an unlinked file of the
  build dir). The test then sees only read-only inputs in the store and cannot rewrite its own
  log or result.
- A372: if the inputs cannot be locked the build fails (ExitStep, last line names the reason);
  no unlocked fallback (AGENTS §2.1/§2.5: a build that can corrupt later builds is data loss).
- A373: the outer bob-builder becomes non-dumpable only after the nested child has started
  (before that the child's /proc/<pid>/uid_map would belong to root and the rootless uid-map
  write fails with EACCES, measured), and the child waits on a release pipe, so no job code runs
  while the outer is still dumpable.
- A374: ambient CAP_SYS_ADMIN is used for the one remount and cleared before the exec into the
  job stage (non-root uid → no capabilities after execve, verified via CapEff).

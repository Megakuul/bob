## DECISIONS
- D-IB20-1 Release project: release.json keeps project "" (bob.RepoOpts has no project; the
  release derivation stays identical between local and remote builds, R-OUT-022/principle 4). A
  manifest with project "" belongs to the building server project: the server (ParseManifest)
  and the worker (staging) put "<project>/" in front of its image repositories. A manifest
  naming another project is still rejected.
- D-IB20-2 Release labels are resolved by the worker from the evaluated graph (release.release
  nodes whose name or label equals the pipeline's Releases entry) and built with the targets;
  they are not added to Report.Targets (the orchestrator's R-PIPE-003 check recomputes targets
  from the definitions and stays unchanged).
- D-IB20-3 Version source: CreateBuild{version} (stored as BuildRecord.vr) wins; else a build
  of refs/tags/<t> uses <t> without "v" when it is a valid release version (also its retries and
  re-runs, which keep the ref); the selection carries it to the worker as `@version:<v>`.
- D-IB20-4 Plain (non-release) image outputs are staged under `<project>/<lower-case package
  name>`; a name that is no valid repository leaves the image a cache path only (not staged).
- D-IB20-5 Image/asset staging errors: upload failures are infra (next attempt), everything
  else (layout, digest, symlink out of the closure, manifest mismatch) fails the job.

# M1.8 brief — red acceptance tests (read after AGENTS.md and HARNESS.md)

Goal: for every SPEC requirement id of your track, write the acceptance test(s) exactly as the
SPEC "Acceptance" text says, registered with `parity.Covers(t, "R-…")`. The features are stubs
(`BOB-E-9008`), so the tests start **red**. They must be red for one reason only: "not
implemented". They must compile, be gofmt-clean, pass `go vet`, and pass the `lint`/`layering`
rules. At Gate H these tests become protected (AGENTS.md §5.2): write them as if they could never
be loosened later. **Correct and strict beats many.** Never skip, never `t.Skip` to go green,
never assert something weaker than the SPEC.

## Where things are
- Shared base: `tests/harness` (`harness.Bin/Run/Fixture/Red/RedFeature`), `tests/parity`
  (`parity.Covers`), `tests/golden` (golden compare), `tests/errors/leakcheck`,
  `tests/serverenv/*` (RustFS, counting proxy `s3count`, chaos, forge fixtures), `tools/devstack`
  (all-in-one stack: `stack.Start`), fixtures in `tests/fixtures/repos/<name>` (`harness.Fixture`).
- SPEC.md (560 KB): read the sections of your track in full (they are listed below). Requirement
  headings are `#### R-<AREA>-<NNN> title`. The acceptance text is binding. `examples/<x>` in SPEC
  means `tests/fixtures/repos/<x>`.
- Suite directories are fixed by HARNESS.md §14 (`tests/<suite>/`, package named after the suite).

## How a red test looks
```go
func TestRFW015LabelGrammar(t *testing.T) {
    parity.Covers(t, "R-FW-015")
    r := harness.Run(t, "bob", harness.Spec{Dir: harness.Fixture(t, "acme")}, "graph", "--json")
    if harness.Red(t, r) { return }          // fails the test with "red: not implemented yet: …"
    // …the real assertions from the SPEC acceptance text, written out in full…
}
```
Library-level tests (e.g. `pkg/bob` constructors) import the package as SPEC defines it. If the
declaration does not exist yet, add a **stub in your own package** with the SPEC signature that
returns `diag.NotImplemented("<feature>")` (or the zero value plus error), and let the test call
`harness.RedFeature` when it gets that error. Stubs follow the lint rules (no panic, no globals).
Tests that need a stack use `tools/devstack/stack.Start` (RustFS + proxy + server processes) and
end server e2e tests with the S3 counting proxy's `AssertNoList`.

Requirements marked `(manual)` in SPEC: do not write a test; list them in your report (the
coordinator records them in `tests/parity/manual.json`). Requirements whose acceptance needs a
resource this host lacks (x86_64 hardware, real AppArmor, GPUs): follow HARNESS.md for what is
tested here and what is `(manual)`.
Budgets: do not write budget tests (the budgets stage owns them) unless the SPEC acceptance text
itself is the budget; reference budget ids from `tests/budgets/budgets.json` in a comment.

## Rules (all tracks)
1. You own only the directories listed for your track. Do **not** edit `tools/ci`, `tools/lint`,
   `go.mod`/`go.sum`, `tests/protected.sha256`, `tests/parity/*`, `plan/*`, `docs/*`,
   `REQUIREMENTS.md`, `SPEC.md`, or other tracks' directories. If you need a new Go dependency or
   a change in a file you do not own, say so in your report; do not work around it.
2. **Do not commit.** The coordinator commits per task (decision A25).
3. Use your own caches: `export CGO_ENABLED=0 GOCACHE=/root/.cache/go-build-<track>
   XDG_CACHE_HOME=/root/.cache/bobxdg-<track>`; ports only from the range in your track
   (serverenv `FreePort` picks from 23000–23999; do not hard-code ports).
4. Verify only your own packages while others are editing: `go vet ./tests/<yours>/...
   ./pkg/<yours>/...`, `go test ./tests/<yours>/...` (red failures are expected; compile errors,
   panics, hangs and "harness error" are not). Run `go run ./tools/lint/cmd/boblint …` /
   `go run ./tools/ci -only fmt,vet,lint,layering` at the end and fix what is yours.
5. Hostile and slow: every test has a timeout (≤ 5 min), cleans up its processes (use
   `serverenv.Process`; it dies with the test binary), and leaves no goroutine or port behind.
6. No raw Nix text may appear in anything a test treats as user output (use
   `tests/errors/leakcheck` on captured output).
7. Anything you decide that the SPEC leaves open: pick the SPEC's written recommendation, and list
   it in your report under "Decisions" (the coordinator records it in plan/decisions.md).
8. SPEC contradictions or untestable acceptance texts: do not "fix" the test. Write the test as far
   as it can be written, and list the problem under "SPEC problems" with the R-id and quote.

## Report (your final message, ≤ 80 lines)
- R-ids covered (count, grouped), R-ids not covered and why (manual / blocked / SPEC problem);
- files created, stubs added in `pkg/…`;
- suites and the command that runs each; how many tests are red, and confirmation that every red
  is a "not implemented" red (paste one sample failure line per suite);
- Decisions, SPEC problems, new dependencies needed, files you could not own;
- anything the CI wiring (stage `acceptance`) must know (build tags, env vars, long tests).

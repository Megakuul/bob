This guide shows how to work on a bob project day to day: a shell with the right toolchains,
editors that find the right language servers, and automatic activation when you `cd` into a
project.

## What a dev shell contains

Every project has a dev shell named `default`, even without a declaration. It contains the
toolchains of the ecosystems the project uses, at the versions of its nixpkgs pin:

| Ecosystem | Tools |
|---|---|
| Go | `go`, `gofmt`, `gopls` (always present) |
| C/C++ | `gcc`, `g++`, `cc`, `c++`, `clangd`, `clang-format` |
| Rust | `rustc`, `cargo`, `rust-analyzer`, the standard library sources |
| npm | `node`, `npm`, `npx`, `tsc`/`tsserver`, plus the commands of each importer's direct dependencies (`vite`, `vitest`, …) |
| OCaml | the compiler and tools of the pin |

Declare extra tools, variables and hooks with `bob.NewShell` in a `bob.go`:

```go verify
//go:build bob

package acme

import (
	"github.com/megakuul/bob/pkg/bob"
	"github.com/megakuul/bob/pkg/nixpkgs"
)

// Dev is the default dev shell.
var Dev = bob.Define(func(p *bob.P) *bob.Shell {
	return bob.NewShell(p, bob.DevShell{
		Packages: []bob.Tool{nixpkgs.Jq.Tool(p), nixpkgs.Postgresql.Tool(p)},
		Env:      map[string]string{"ACME_ENV": "dev"},
		Hooks:    []string{"mkdir -p .cache"},
	})
})
```

> [!NOTE]
> The toolchains in the table above are added without declaring them; `Packages` is for
> extra tools.

Several shells are allowed; give each a `Name` and pick one with `--shell <name>`. A shell
name that does not exist is `BOB-E-1014`.

## bob dev

`bob dev` evaluates the project, prepares the working tree (native files, generated code,
`node_modules`), runs the hooks, and starts your `$SHELL` with the toolchains on `PATH`:

```text
$ bob dev
bob: dev shell default (go 1.26.8, gopls 0.22.0) · 0.8s
$ go version
go version go1.26.8 linux/arm64
$ exit
```

Inside, `BOB_DEV=1`, `BOB_PROJECT=<root>` and `BOB_DEV_SHELL=<name>` are set, so prompts and
scripts can tell. bob does not change your prompt. When the shell exits, `bob dev` exits with
its status.

Run one command instead of a shell after `--`:

```bash
bob dev -- go test ./...
bob dev -- sh -c 'go vet ./... && go test ./...'
```

The command is looked up in the dev shell first (its toolchains and tools), then on your own
`PATH`, so an editor installed on your machine works too (`bob dev -- code .`).

Dev servers: `bob.DevShell{Servers: …}` is accepted, but `bob dev` does not start servers
yet (`--servers-only` reports `dev shell default has no dev servers`). Start them inside the
shell yourself, for example `bob dev -- sh -c 'cd web && vite'`. (Dev servers are part of the
Vite live-reload work that is not finished yet; see [Limitations](../07-reference/03-status.md).)

## bob exec and the .bob/bin shims

`bob exec -- <tool> [args]` runs one tool of the dev shell, with the tool's own exit status:

```text
$ bob exec -- go version
go version go1.26.8 linux/arm64
```

bob also writes a shim per tool into `.bob/bin`. A shim is a two-line script that calls
`bob exec`, so the tool runs inside bob's namespace with the dev shell's environment:

```sh
#!/bin/sh
# Code generated by bob. DO NOT EDIT.
exec "${BOB:-/home/you/.local/bin/bob}" exec --project '/home/you/hello-go' -- go "$@"
```

Language servers (`gopls`, `clangd`, `rust-analyzer`, `typescript-language-server`,
`ocamllsp` and a few more) get `bob exec --lsp`. The LSP proxy rewrites `/nix/store/…` paths
in the messages to their location in bob's store on your disk, so "go to definition" into the
standard library or a dependency opens a real file in an editor that runs outside the
namespace. `bob env` also fetches the headers of the nixpkgs libraries your C/C++ packages use,
so `clangd` resolves every include of `compile_commands.json` before the first build.

If you move the bob binary, set `BOB` to its new path, or let bob rewrite the shims (any
evaluating command does). A shim of a project whose `.bob/` was deleted fails with
`BOB-E-7006`; run `bob env` in that project.

## The shell hook

With the hook, `cd` into a project puts its `.bob/bin` first on `PATH` and exports the dev
shell's plain variables; `cd` out restores your environment exactly. The hook never enters the
namespace and does nothing on most prompts, so it is fast.

Install it once:

| Shell | Line in your rc file |
|---|---|
| bash (`~/.bashrc`) | `eval "$(bob hook bash)"` |
| zsh (`~/.zshrc`) | `eval "$(bob hook zsh)"` |
| fish (`~/.config/fish/config.fish`) | `bob hook fish \| source` |

The hook runs project code (it evaluates `bob.go`), so it activates only projects you allowed:

```text
$ cd hello-go
bob: /home/you/hello-go is not allowed; run 'bob allow' to load its environment
$ bob allow
bob: allowed /home/you/hello-go
$ command -v go
/home/you/hello-go/.bob/bin/go
$ cd ..
$ command -v go
(your previous go, or nothing)
```

`bob deny [dir]` removes the permission. Allowed roots are stored by path in
`~/.local/state/bob/allow.json`. Explicit commands such as `bob build` and `bob dev` need no
`bob allow`.

The hook keeps its state in a few variables: `BOB_PROJECT` (the active root),
`BOB_ENV_HASH`, `BOB_ENV_RESTORE` (what to restore when you leave) and `BOB_DENIED_SEEN`
(projects it already told you about).

> [!NOTE]
> The bash hook is tested here; the zsh and fish hooks are generated from the same code but
> were not run in real zsh and fish sessions on the documentation host.

### Without a hook: direnv and scripts

`bob env` prints the same "enter" script for the current project. Use it with direnv
(`.envrc`: `eval "$(bob env)"`) or in editor launch scripts. `--format fish` prints fish
syntax; `--format json` prints the data:

```text
$ bob env --format json
{"root":"/home/you/hello-go","shell":"default","outside":{"set":{"CGO_ENABLED":"0"},"prepend":{"PATH":["/home/you/hello-go/.bob/bin"]}},"insideOnly":["GOROOT"],"tools":["go","gofmt","gopls"]}
```

Variables whose values point into bob's store (such as `GOROOT`) are only set inside the
namespace (`insideOnly`); outside, tools reach them through the shims.

## Editors

`bob editor <name>` prints what an editor needs; `--write` merges it into the project's
settings file (other keys are kept).

| Editor | What to do |
|---|---|
| Neovim, Helix, Emacs, Sublime | nothing: with the shell hook, the language servers resolve to `.bob/bin` on `PATH` |
| Zed | works with the hook; `bob editor zed --write` adds `lsp.<server>.binary.path` entries for builds that ignore `PATH` |
| VS Code (Go, rust-analyzer, clangd extensions) | `bob editor vscode --write` writes `.vscode/settings.json` pointing at `.bob/bin` |
| VS Code built-in TypeScript, JetBrains IDEs | they read toolchain files themselves: start them inside the dev shell, `bob dev -- code --new-window .` or `bob dev -- idea .` |

For a Go project, `bob editor vscode` prints:

```json
{
  "files.watcherExclude": {
    "**/.bob/**": true
  },
  "go.alternateTools": {
    "go": "${workspaceFolder}/.bob/bin/go",
    "gopls": "${workspaceFolder}/.bob/bin/gopls"
  },
  "go.toolsManagement.autoUpdate": false,
  "gopls": {
    "build.buildFlags": [
      "-tags=bob"
    ],
    "build.directoryFilters": [
      "-.bob"
    ]
  }
}
```

`-tags=bob` makes gopls type-check your `bob.go` files too, so completion and "go to
definition" work in build definitions. The `gopls` shim sets it already.
